# Linux imaging deep-dive

How Linux deployments work in deployserver. Companion to `docs/WINDOWS.md`.

## 1. The two flows

There are two ways we image Linux:

1. **Network installer** (autoinstall / kickstart / preseed). The
   target boots a stock distro installer kernel + initrd, which
   fetches an answer file from the deploy server and proceeds
   unattended. This is the default, because it's well-documented by
   each distro and inherits all of upstream's hardware support.

2. **Image apply** (golden qcow2 or raw image, `dd`'d to disk). Faster
   and more reproducible, but you build the image yourself with
   `virt-customize` or equivalent, and hardware variations are your
   problem. Use this for fleets where the targets are identical.

v1 ships flow #1 fully; flow #2 is a documented Linux-side recipe but
not a first-class API path.

## 2. Per-distro answer files

Generated server-side per machine, served from
`/boot/<machine_id>/user-data` (cloud-init schema, NoCloud datasource).

### Ubuntu autoinstall (24.04 / 22.04)

iPXE script (auto-generated by `services/http-boot/scripts/render`):

```
kernel <KERNEL_URL> initrd=initrd.img \
    autoinstall \
    ds=nocloud-net;s=https://$DEPLOY_FQDN/boot/<id>/ \
    ip=dhcp
initrd <INITRD_URL>
boot
```

The `s=` URL ends with a trailing slash; subiquity GETs
`s=...user-data`, `s=...meta-data`, `s=...vendor-data`. Our render
service serves all three; user-data carries the autoinstall
specification:

```yaml
#cloud-config
autoinstall:
  version: 1
  identity:
    hostname: {{ machine.asset_tag }}
    username: {{ profile.vars.local_user }}
    password: '{{ profile.vars.local_user_pwhash }}'   # mkpasswd -m sha-512
  ssh:
    install-server: yes
    authorized-keys:
      {{ profile.vars.authorized_keys }}
  storage:
    layout:
      name: lvm
  packages: {{ profile.vars.packages | toJSON }}
  late-commands:
    - curtin in-target -- curl -sf https://{{ deploy_fqdn }}/v1/jobs/{{ job_id }}/events?token={{ one_shot_token }} -d '{"phase":"completed","message":"Ubuntu autoinstall finished"}'
```

The `late-commands` phone-home uses the same one-shot token mechanism
as the Windows path, transitioning the deployment to `completed`.

### Debian preseed (12+)

Less commonly used than autoinstall. preseed takes a flat
key/value file. We render:

```
d-i debian-installer/locale string en_US.UTF-8
d-i netcfg/get_hostname string {{ machine.asset_tag }}
d-i passwd/user-fullname string {{ profile.vars.full_name }}
...
d-i preseed/late_command string in-target curl -sf "https://{{ deploy_fqdn }}/v1/jobs/{{ job_id }}/events?token={{ one_shot_token }}" -d '{"phase":"completed","message":"preseed done"}'
```

iPXE script:
```
kernel ... auto=true priority=critical preseed/url=https://$DEPLOY_FQDN/boot/<id>/preseed
```

### RHEL/Rocky/Alma kickstart (9+)

```
text
lang en_US.UTF-8
keyboard us
timezone {{ profile.vars.timezone | default "UTC" }}
network --hostname={{ machine.asset_tag }} --bootproto=dhcp
rootpw --iscrypted {{ profile.vars.root_pwhash }}
authselect select sssd
%post
curl -sf "https://{{ deploy_fqdn }}/v1/jobs/{{ job_id }}/events?token={{ one_shot_token }}" -d '{"phase":"completed","message":"ks done"}'
%end
```

iPXE script:
```
kernel ... inst.ks=https://$DEPLOY_FQDN/boot/<id>/ks.cfg
```

### Fedora autoinstall

Same kickstart format as RHEL above; just a different kernel/initrd
URL.

## 3. Image apply (flow #2)

Build a golden image once:

```sh
sudo virt-builder ubuntu-24.04 \
    --output golden-2404.qcow2 \
    --root-password password:CHANGE_ME \
    --hostname {{ template-placeholder }} \
    --update \
    --install python3,curl,openssh-server \
    --run-command 'systemctl enable ssh' \
    --run-command 'cloud-init clean'

# Convert to raw + sparse for streaming:
qemu-img convert -O raw -S 4k golden-2404.qcow2 golden-2404.raw
xz -T 0 golden-2404.raw   # → golden-2404.raw.xz

# Upload:
deployctl images upload \
    --name ubuntu-2404-golden \
    --os linux --version 24.04 --arch amd64 \
    --version-tag 2026.04 \
    golden-2404.raw.xz
```

The boot flow:

1. iPXE script kexecs into a small "imaging initramfs" (we ship
   `imaging-init.cpio.gz` which is just busybox + curl + xzcat + dd).
2. Imaging-init fetches the raw.xz image, pipes through `xzcat | dd
   of=/dev/sdX bs=4M`, runs `cloud-init clean`, and reboots.
3. Cloud-init runs on first boot of the imaged disk and applies the
   per-machine config (hostname, network, late-commands).

This flow trades hardware-independence for speed. Use it when you
control the hardware fleet.

## 4. Drivers

Linux's hardware support is largely in-tree. We do not ship driver
packs for Linux deployments. If you need out-of-tree modules
(e.g. proprietary NVIDIA), put them in cloud-init's `runcmd` to
install via DKMS post-install.

## 5. BitLocker / LUKS / TPM

LUKS with TPM2 unlock is supported via cloud-init `bootcmd` running
`systemd-cryptenroll --tpm2-device=auto /dev/sdX`. The recovery
passphrase is reported back to the API via the same one-shot-token
phone-home mechanism Windows uses for BitLocker recovery keys; stored
encrypted in `deployment_jobs.result`.

## 6. Known limitations

- ARM64 Linux is supported in principle (autoinstall is arch-agnostic),
  but v1 only validates amd64.
- We don't ship a Linux equivalent of Windows' driver-pack ingestion.
  If a target needs an out-of-tree module to even boot the installer
  (rare), use the image-apply flow with the module pre-installed.
