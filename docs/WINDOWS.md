# Windows imaging deep-dive

This document is the reference for how Windows deployments work in
deployserver. It covers reference-image capture, WinPE construction,
driver-pack ingestion + matching, the unattend pipeline, and the
specifics of activation, BitLocker, and TPM ownership.

## 1. Capture: making a hardware-independent reference image

The user must do this once per Windows edition you want to deploy. We
do not redistribute Microsoft binaries.

1. Spin up a fresh VM (Hyper-V Gen 2 or KVM with OVMF) with the matching
   Windows ISO. Choose **Windows 10/11 Pro** or **Server**. ARM64 is
   supported in principle; v1 only validates amd64.
2. At the first OOBE, press **Ctrl+Shift+F3** to enter audit mode.
3. Install your baseline software, Windows Updates, etc. Do **not**
   install vendor-specific drivers. The image must stay hardware-clean.
4. Sysprep:
   ```
   C:\Windows\System32\Sysprep\sysprep.exe /generalize /oobe /shutdown ^
       /unattend:C:\unattend-capture.xml
   ```
   Use the capture-only unattend (`docs/templates/unattend-capture.xml`,
   not in v1) which sets `CopyProfile=true` so the default user profile
   carries your customizations.
5. Boot a WinPE you've built (see §2) and capture:
   ```
   DISM /Capture-Image /ImageFile:E:\install.wim ^
        /CaptureDir:C:\ /Name:"baseline" /Compress:max /CheckIntegrity
   ```
6. Upload to deployserver:
   ```
   deployctl images upload \
       --name win11-baseline \
       --os windows --version 11 --arch amd64 \
       --version-tag 2026.04 \
       install.wim
   ```

The same WIM deploys to any vendor's hardware. Vendor-specific things
go in driver packs, not in the WIM.

## 2. WinPE that boots over the network

Two boot artifacts exist:

- `boot.wim` — a customized WinPE x64 that gets HTTP-loaded by iPXE's
  `wimboot`. Lives in S3 as a static blob; its URL goes into the
  per-machine iPXE script generated by http-boot.
- `wimboot` itself — an iPXE-aware loader that can be initrd'd. Pinned
  to a known release SHA in `winpe/wimboot.sha256`.

### Building boot.wim

This step needs a Windows host with the **Windows ADK + Windows PE
add-on** installed. It is a one-time setup; the PowerShell script is
in `winpe/scripts/build-boot-wim.ps1` (TODO; tracked in STATUS.md).
Outline:

1. `copype amd64 C:\WinPE_amd64`
2. `Mount-WindowsImage -ImagePath C:\WinPE_amd64\media\sources\boot.wim -Index 1 -Path C:\Mount`
3. Add packages we need: `WinPE-WMI`, `WinPE-NetFX`, `WinPE-Scripting`,
   `WinPE-PowerShell`, `WinPE-DismCmdlets`, `WinPE-EnhancedStorage`,
   `WinPE-StorageWMI`. **Do not** add WinPE-Setup; we apply WIMs
   directly with DISM.
4. Add curl: `curl.exe` from the Microsoft Store cURL release into
   `C:\Mount\Windows\System32\`.
5. Drop in our scripts:
   - `winpe/scripts/startnet.cmd` → `C:\Mount\Windows\System32\startnet.cmd`
   - `winpe/scripts/deploy.cmd` is fetched at runtime, not baked.
6. Drop in the deploy-CA pinning bundle:
   - `winpe/scripts/deploy-ca.pem` → `X:\deploy\deploy-ca.pem` via the
     boot-time `init` (X: is the WinPE in-memory drive — copy it during
     WinPE setup to a known location).
7. `Dismount-WindowsImage -Path C:\Mount -Save`
8. Upload `boot.wim` to deployserver:
   ```
   deployctl winpe upload boot.wim
   ```

The result: a WinPE that, when booted via wimboot, reads
`startnet.cmd`, fetches `deploy.cmd` over HTTPS-with-pinned-CA, and
runs it.

## 3. Driver packs

### Layout on disk (in S3)

```
drivers/
  dell/
    latitude-7440/
      win11/
        2025.10/
          drivers.zip            (extracted .inf tree, e.g. from Dell DCU)
          manifest.json          (rules, see §3a)
  hp/
    elitebook-865-g11/
      ...
```

### 3a. Manifest format

Each driver-pack version has a `manifest.json`:

```json
{
  "version": "2025.10",
  "vendor":  "Dell",
  "model":   "Latitude 7440",
  "os_family":   "windows",
  "os_version":  "11",
  "rules": [
    { "type": "dmi-product", "value": "Latitude 7440" },
    { "type": "pci-vid-did", "value": "8086:1521" }
  ]
}
```

The matching engine (`services/api/internal/driverpack/match.go`) is
the source of truth for precedence.

### 3b. Ingestion

```
deployctl driver-packs ingest \
    --vendor Dell --model "Latitude 7440" \
    --os windows --os-version 11 \
    --version-tag 2025.10 \
    drivers.zip manifest.json
```

The ingestion job:
1. Stores `drivers.zip` as a content-addressed blob.
2. Inserts `driver_packs`, `driver_pack_versions`, and
   `driver_match_rules` rows.
3. Optionally validates by inspecting the .inf files and confirming
   the rules are consistent (planned, not implemented in v1).

## 4. Apply

`winpe/scripts/deploy.cmd` is fetched fresh on every boot. It:

1. Fingerprints the machine via `wmic baseboard`, `wmic computersystem`,
   and `pnputil /enum-devices`.
2. POSTs the fingerprint to `/v1/winpe/plan`. The API runs the
   matcher, returns a plan JSON with image URL, driver-pack URLs,
   unattend URL.
3. `diskpart` partitions disk 0 (GPT, ESP + MSR + Windows + Recovery).
4. `DISM /Apply-Image` from the streamed WIM.
5. Downloads matched driver packs into `W:\Drivers`, runs
   `DISM /Image:W:\ /Add-Driver /Recurse`.
6. Fetches the rendered unattend.xml from
   `/v1/winpe/unattend.xml` (token-bound) and writes it to
   `W:\Windows\Panther\unattend.xml`.
7. `bcdboot W:\Windows /s S: /f UEFI`.
8. POSTs deployment events to `/v1/jobs/<id>/events` for the operator UI.
9. `wpeutil reboot`.

## 5. unattend.xml templating

`services/api/internal/answerfile/unattend.go` renders unattend XML
from a Go text/template stored per-profile in the
`answer_file_templates` table. The template author can use:

- `{{.Machine.AssetTag}}`, `{{.Machine.MAC}}`
- `{{.Profile.Vars.<key>}}` (free-form jsonb supplied at issuance time)
- `{{.Image.OSEdition}}`, `{{.Image.Locale}}`, `{{.Image.Timezone}}`
- `{{.LocalAdmin.PasswordPlain | accountPassword}}` — encodes to the
  base64(UTF-16LE(password+"Password")) form Windows expects
- `{{ if .DomainJoin }}...{{ end }}` — domain-join section is rendered
  iff a one-shot domain-join token was bound to this auth code at
  issuance time

The `LocalAdmin.PasswordPlain` field never appears in the rendered
output; only the encoded form does. We rely on the Go template engine
to refuse to interpolate the field when the user templates it without
the encoder helper, but operators are still expected to use
`accountPassword` in their templates.

## 6. Activation, BitLocker, TPM

- **Activation:** out of scope for deployserver. Use one of:
  - **KMS** — set `ProductKey` to your KMS client setup key in unattend
    `Microsoft-Windows-Shell-Setup`.
  - **MAK** — embed the MAK in the unattend (it gets activated on first
    internet contact; KMS is preferred for fleet).
  - **Autopilot** — separate path; set up the device via Microsoft
    Endpoint Manager, deployserver only delivers the OOBE-ready image.
- **BitLocker:** if `Profile.Vars.bitlocker == true`, the unattend
  template should include a SetupComplete.cmd that runs
  `manage-bde -on C: -RecoveryPassword`. The recovery password posts
  back to the API via the deployment events endpoint and is stored
  encrypted in `deployment_jobs.result`.
- **TPM ownership:** Windows 11 takes TPM ownership during specialize
  automatically when TPM 2.0 is present. No deployserver action.

## 7. Known gaps in v1

- `winpe/scripts/build-boot-wim.ps1` is referenced but not yet
  delivered.
- `deploy.cmd`'s PCI VID/DID extraction loop is incomplete — the
  pnputil parsing leaves the variables only partly extracted. v1 will
  skip PCI matching from WinPE and rely on DMI; PCI matching is added
  via a separate Go tool injected into WinPE in v2.
- ARM64 Windows is documented but not validated.
- BitLocker recovery key escrow is sketched but not implemented.
- KMS / MAK helpers in the operator UI are not implemented.

See `docs/STATUS.md` for the live tracker.
